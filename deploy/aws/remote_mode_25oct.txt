Remote mode: a live recording that uses the AWS agent service (25 Oct 2026)

What it is
brain/brain/agent/remote_forward.py is a local forwarder. Unity's recorder calls it exactly as it calls the local
agent server. For each call it uploads the robot's own sensor files that the remote route reads (PUT /runs ZIP batches;
pull-v1 for agent steps), forwards the call to the ALB with the X-Origin-Verify header and returns the AWS answer.
No Unity change is needed: the recorder already reads SMOKE_AGENT_URL.

How to start it
  cd /Volumes/Tashon/opencv/smoke-rescue/brain
  SMOKE_FORWARD_LOG=../data/runs/remote_forward_25oct/live.jsonl \
    .venv/bin/uvicorn brain.agent.remote_forward:app --host 127.0.0.1 --port 8095
Optional: SMOKE_FALLBACK_URL=http://127.0.0.1:8080 (a local agent server used when AWS fails, see below).
The header value is read once from Secrets Manager smoke-rescue/origin-verify with the local aws cli (or from
SMOKE_ORIGIN_HEADER_FILE / SMOKE_ORIGIN_VERIFY). It is never printed.
Check: curl -s http://127.0.0.1:8095/health  (AWS /health plus a "forwarder" block; 503 if AWS is unreachable)
Live counts and latencies: curl -s http://127.0.0.1:8095/forwarder/stats

Pointing Unity at it
Unity reads SMOKE_AGENT_URL when a recording starts (RecorderMenu.cs). The editor must be launched with
SMOKE_AGENT_URL=http://127.0.0.1:8095 in its environment (for example from Unity Hub started in a shell that exports it).
Do not use port 8090: the Unity editor itself listens on [::1]:8090 (mcp-unity). Use 127.0.0.1, not localhost: the
forwarder binds IPv4 only.

Agent steps on AWS do not work today (measured, root cause found)
Every AWS robot and commander step returned HTTP 200 with summary null, no orders and no evidence. The AWS trace shows
model_error: Azure HTTP 400 "Function tools with reasoning_effort are not supported for this model". The backend
resends without reasoning_effort, but that resend counted as an attempt, and the task definition sets
AZURE_OPENAI_MAX_ATTEMPTS=1 (agent.yaml line 406), so the resend never happened. Locally the default is 4, which is why
local steps work. Reproduced locally with AZURE_OPENAI_MAX_ATTEMPTS=1: same 400.
Fixed in code: brain/brain/agent/llm.py no longer counts that resend (test_aws_backends.py, fails on the old code).
The running image still has the old code. To make AWS agent steps work, one of:
  a) rebuild and push the agent image and redeploy (deploy/aws/deploy.sh; needs docker, loads the machine), or
  b) a stack update setting AZURE_OPENAI_MAX_ATTEMPTS to 2 in agent.yaml (no rebuild; a CloudFormation change).
Neither was done here: both were outside what this task allowed.
Pull-v1 itself works on AWS: the 6 steps completed their pull job (about 1.0 MB each) and the model call was the only
failure. Steps were not compared with local answers because AWS produced none; the model is not deterministic anyway,
and remote steps skip the local code-run pre-scan by design (commit d587520d), so even working steps will differ.
Known difference in evidence ids: track_fire_spread on the pull path loads depth+thermal only, so its frame id differs
from a local run; its measurements are equal (test_pull_transport.py, test_remote_forward.py). Latest-frame tools keep
the local evidence id because the forwarder sends X-Recording-Source with the local robot folder.

Failure behaviour
- AWS unreachable, timeout, or 5xx: never an empty answer. Without SMOKE_FALLBACK_URL the forwarder returns HTTP 502 with
  the reason (Unity logs "agent ...: HTTP 502" and treats the call as failed). With a fallback, the original request goes
  to the fallback and the response carries X-Smoke-Served-By: fallback, with a WARNING in the forwarder log.
- A remote step the model never answered (the case above) is also a 502 or a fallback, not an empty 200. That matters:
  Unity counts failed agent calls and after 3 in a row lets the robot confirm people itself; an empty 200 would keep it
  waiting on a dead agent.
- A 4xx from AWS (e.g. a missing frame) is returned unchanged; it means a forwarder or request bug and is not hidden.
- /health returns 503 when AWS is down and no fallback is healthy, so Unity starts with the colour detector off and says
  so in its console ("vision service ... not reachable").
- Mixed state with a fallback: place databases and 3D maps live on whichever server answered. A place keyframe served by
  the fallback has another database_id, so Unity resets its keyframe table (existing behaviour).

Cost to a 550 s mission (estimate from the measurements above, directional)
The person scan and the integrate after it are synchronous in the recorder. Per robot scan AWS costs about 3.3 s against
about 1.7 s locally (replay, measured under the same load), so about +1.6 s per scan. At one scan per sim second per robot
(more while a person is in view) that adds about 550 x 2 x 1.6 = 1760 s, about 30 minutes, to a mission whose local wall
time in perf.txt was about 95 s per 10 sim seconds (about 87 minutes). Simulation outcomes do not change: the recorder is
offline and pauses while it waits. Agent steps would add about 1 to 3 s of transport each, once they work.
