Verdict
-------
Done and verified locally: an MCP server with four tools (stdio and streamable HTTP), an inline-frame robot route on
the FastAPI service, OpenAPI docs with the public AWS routes written into them, a 27-line robot client, 8 pytest tests
that fail when the behaviour they test is broken, and examples/README.txt. Every tool was called for real over both
transports. One gap on AWS: the deployed service predates the inline-frame route, so detect_people with the remote
backend answers HTTP 500 there until brain/brain/agent/server.py is redeployed. I did not deploy (not allowed). The
same remote path works against a local instance of the updated server.

Tools
-----
detect_people(image, depth?, depth_scale, intrinsics?, min_conf, backend?)  vision.detect_people_rgb (YOLO11m, cv2.dnn)
assess_visibility(image, depth?, depth_scale, backend?)                     vision.assess_visibility
match_place(keyframe_a, keyframe_b, return_payloads)                        place.make_keyframe + place.match_keyframes
describe_scene_heat(thermal, rgb?, depth?, depth_scale, backend?)           vision.scan_thermal + band statistics
Backends: local (default) runs that code in the MCP process. remote posts to SMOKE_API_URL (default the public Lambda
URL .../api): /perceive/people, /vision/assess_visibility, /vision/scan_thermal. match_place is always local because
no public route takes two keyframes; its result says backend "local". Remote results are what the route returns, so
their fields differ from local ones (remote visibility has no usable_rgb verdict and computes dark_channel as a mean;
remote heat has pixel regions only). New constants each have a *_REASON sibling (DEFAULT_API_URL, REMOTE_TIMEOUT_S,
DEFAULT_HTTP_PORT, DEFAULT_MIN_CONF in mcp_server.py; DEFAULT_DEPTH_SCALE in robot_frame.py). No config file changed.

describe_scene_heat works with the data we have: the recordings carry 16-bit thermal frames (kelvin x 10), and the tool
runs the robots' own scan_thermal. Hot-region ranges come from depth when the region has it; flames return no depth, so
the fire fixture gets an upper bound from the floor geometry (9.45 m, range_source floor_upper_bound). I did not check
that bound against ground truth.

deploy/aws/site_lambda.yaml and a deploy; I did neither.

Not done or not verified
------------------------
- detect_people through AWS: needs server.py redeployed; HTTP 500 today. Verified only against a local instance.
- OpenAPI docs are not reachable through the public Lambda front (404); they are on any local instance.
- match_place has no remote path (no stateless public route); it runs locally in both modes and says so.
- Ranges, floor gaps and place keyframes assume our camera mast (1.6 m, 10 deg down); another robot gets biased ranges.
  vision.py reads the mount from config/sensors.json directly, so the MCP tools cannot override it without editing
  vision.py, which I left alone.
- describe_scene_heat without rgb runs the colour detector on a black image inside scan_thermal (about 2 s, wasted);
  rgb_people is reported as null in that case rather than an empty list.
- The fire hotspot's 9.45 m floor upper bound was not compared with ground truth.
- Detector times here (1.8 to 7 s) were measured while other jobs shared the machine; perception.json gives 1.3 s idle.
- Not tested from a real ROS node or from an MCP desktop client itself.
