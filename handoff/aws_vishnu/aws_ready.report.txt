Audit of the current server and image.
The server has 14 application routes. GET /health reports backend, model, OpenCV and approval mode without calling the model or loading YOLO. POST /robot/{robot}/step runs the robot agent and its perception/action tools. It needs a readable robot_dir, sensor history when tools request it, and writable trace/debug paths. POST /commander/step uses the configured LLM and a writable trace. POST /approval, GET /approvals and POST /approvals/{aid} keep approval state in memory and append to the trace. GET /trace returns up to 2,000 trace records. None of these routes needs a scene model or a DINO model.
POST /vision/{tool} accepts an uploaded PNG or JPEG, including multipart. Its supported tools are assess_visibility and scan_thermal. The latter needs uint16 thermal PNG values in kelvin times ten. These image-only routes do not load the YOLO model or require a recording folder. Multipart uses the standard-library email parser, so python-multipart is not missing.
POST /perceive/people loads camera.yaml, thermal.yaml, rgb.txt, depth.txt, thermal.txt, and the corresponding RGB, uint16 depth and uint16 thermal PNGs from robot_dir. lidar.txt is optional and contains its own calibration header. Its only neural model is data/models/onnx/yolo11m.onnx, loaded by cv2.dnn.readNetFromONNX. The existing detector returns an empty list if that file is absent, so a missing model can look like a successful detection of nobody.
POST /map3d/{robot}/integrate reads camera.yaml, depth.txt and depth PNGs, then updates that robot's OpenCV HashTSDF worker. POST /map3d/{robot}/layers returns packed height and visibility arrays. POST /map3d/{robot}/export writes a PLY at the requested server-side path. POST /place/{robot}/keyframe reads that robot's RGB-D recording and stores an ORB keyframe. POST /place/{robot}/match compares a partner payload with the robot's keyframes. ORB needs no downloaded weights, vocabulary, Torch, DINOv2 or learned place model. brain/brain/place.py is a different offline learned-place implementation and is not imported by this server.
FastAPI also registers GET/HEAD /openapi.json, /docs, /docs/oauth2-redirect and /redoc. The ALB forwards every path after the origin-header check. CloudFront accepts the API under /api/* and removes /api before forwarding. A Unity URL using CloudFront must therefore end in /api. The server still receives /health, /robot/... and the other unprefixed routes.
The current server reads config/brain.json and config/actuators.json at import, plus config/perception.json and config/sensors.json in tools and vision. Map3D reads config/map3d.json and config/sensors.json. ORB place reads config/perception.json and config/sensors.json. config/team.json does not exist in this worktree at 0e91e3a, and no current server module reads it. I did not invent its contents or copy it from the other engineer's worktree. The image now copies config/*.json through its build context, so team.json will be included after it is added here and the image is rebuilt. The deployment tag now includes config contents, so a config change cannot reuse an image tag calculated without that change.
The old Dockerfile copied brain/brain to /app/brain. In that layout, parents[3] in agent modules resolves to /, so imports look for /config rather than /app/config. It also copied no config directory and no YOLO weights. The image now preserves the source layout at /app/brain/brain, sets PYTHONPATH=/app/brain, and installs config at /app/config. The build context permits the config and build helper files while excluding recordings, home-directory credentials, Python caches, oracle readers and the evaluator/viewer entry points.
The image now exports YOLO11m during a disposable build stage from Ultralytics' versioned v8.3.0 weight URL. It uses the locked Torch, torchvision and Ultralytics packages, plus explicitly pinned onnx 1.17.0 and protobuf 5.29.3. Export settings are CPU, batch 1, 640 square input, opset 12, fixed shape, no graph simplification and no embedded NMS. The runtime gets only /app/data/models/onnx/yolo11m.onnx. Torch, torchvision and Ultralytics remain outside the runtime. The upstream weight URL is versioned but its bytes are not pinned by a recorded checksum. Download, export and ARM64 DNN inference remain unverified here because the Docker daemon is inaccessible.

Server blocking calls and timeout values.
OllamaBackend.chat makes a synchronous httpx POST to /api/chat with a 300 second phase timeout and no explicit retry loop. It runs inside the robot/commander threadpool once initialized. It is unsuitable for this AWS template's proxy bounds, and the template no longer offers an unconfigured localhost Ollama as an AWS backend. If used outside that template, a 300-500 ms RTT adds to inference latency but is small relative to 300 seconds.
AzureOpenAIBackend.chat makes a synchronous httpx POST. Local defaults are 45 seconds per phase, up to four attempts, and sleeps of 1, 2 and 4 seconds for retriable responses unless Retry-After overrides them, capped at 10 seconds each. It can also remove unsupported reasoning_effort on a 400 response. These are phase timeouts, not one hard wall-clock deadline. The AWS environment now selects 15 seconds and one attempt, with no retry delay. A 300-500 ms Unity-to-AWS RTT is outside this AWS-to-Azure call, so add it to the full response time rather than adding it to each backend attempt. With the single-attempt setting, a deployment rejecting reasoning_effort fails that call instead of taking the local multi-attempt fallback; select a supported Azure deployment/effort before running. Four commander rounds have a nominal 60 seconds of read allowance in AWS, plus connection, write, pool and processing time.
BedrockBackend.chat makes a synchronous Converse call in a worker thread, now with connect=3 seconds, read=20 seconds and one total attempt. Previously the code supplied no timeout or retry config; the installed SDK reports default connect/read values of 60/60 seconds, with retries controlled by SDK/environment settings. IAM credential resolution can itself do HTTP work when backend() first constructs the client on the event-loop thread. The installed container metadata fetcher reports a 2 second request timeout, 3 attempts and a 1 second sleep setting. This is an AWS-local credential path, not the India RTT. Subsequent chats run in the threadpool. Four model rounds have a nominal 92 seconds of connect-plus-read allowance; that arithmetic is not a hard whole-step deadline because timeouts measure phases and socket inactivity.
RobotAgent uses MAX_ROUNDS=4 and STEP_DEADLINE_S=75, checked between model calls. A call already running at 75 seconds is not interrupted. Commander uses up to four rounds and has no whole-step deadline. Threadpool queue waiting has no configured per-request deadline. Bounded client/SDK phases improve failure behavior but do not prove every request finishes within 120 seconds under arbitrary queuing or native work.
RobotMap3D serializes a robot's worker calls under a lock, then polls its pipe for config/map3d.json worker_timeout_s=30. ORB place does the same with config/perception.json place_worker_timeout_s=30. Failure kills and discards that robot's worker and state. Queue/lock acquisition, IPC send and process join have no separate explicit timeout. A 300-500 ms client RTT adds outside the worker poll. HashTSDF's integrate_budget_ms=350 and layers_budget_ms=150 are processing/evaluation budgets, not network deadlines. ORB's 2 second client bound is much shorter than its 30 second server recovery bound. YOLO uses a shared Net lock without a deadline and synchronous native DNN work. That lock serializes two robots' detections. /vision image processing runs directly in its async handler and can block the event loop while OpenCV runs. Image decode and local trace/file writes also have no explicit deadline. /approval does not wait for a human; human mode records a pending answer.
The Docker health check runs every 15 seconds, allows a 3 second check process and a 2 second local urlopen, starts after 20 seconds and retries three times. ECS checks run every 15 seconds with 5 second timeout, 30 second start period and three retries. ALB health checks run every 15 seconds with 5 second timeout and healthy/unhealthy counts 2/3. The ECS grace period is 60 seconds. These checks are AWS-local and do not include the India RTT. Health success still does not establish Bedrock access, model availability or recording access.
The ALB idle timeout changed from 60 to 150 seconds. CloudFront's origin read timeout changed from 60 to 120 seconds, its documented maximum; origin keepalive remains 30 seconds. Uvicorn keepalive remains 75 seconds. Keepalive limits apply between requests rather than limiting an active LLM call. CloudFront's default connection policy is up to three 10 second attempts; it does not retry a timed-out POST response. ECS StopTimeout and target deregistration delay remain 30 seconds, so deploying during an in-flight long step can interrupt it. smoke_test.sh now uses 10 second connection timeouts and retains 30 second health/site and 90 second image-tool totals. A 300-500 ms RTT fits these numbers; several sequential calls still add several RTTs. CloudFront timeout behavior and the allowed 120 second value are documented at https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/DownloadDistValuesOrigin.html and https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-properties-cloudfront-distribution-customoriginconfig.html.
